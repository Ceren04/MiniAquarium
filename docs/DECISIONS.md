# Decisions

One entry per decision that differs from, or is not covered by, the technical specification.

| ID | Decision | Reason |
|---|---|---|
| D-001 | Java 17 is enforced with `options.release = 17` instead of a Gradle toolchain (spec section 3). | A toolchain fails on machines that only have a newer JDK unless an extra plugin downloads JDK 17. `release = 17` gives the same guarantee (Java 17 language and API only) with any JDK 17+. |
| D-002 | The project skeleton is written by hand instead of generated with gdx-liftoff (spec section 3). | Same resulting layout (`domain`, `game`, `desktop`); avoids generated files nobody on the team understands. |
| D-003 | The 70 % coverage gate applies only to the packages listed in `domain/build.gradle` (`coverageGatedPackages`), not to all of `domain` (spec sections 3 and 10). | The base contains skeleton features with empty method bodies; a gate over everything would fail from day one. Each feature is added to the list when it is implemented. |
| D-004 | `SaveData` is `(schemaVersion, time, sections)` where `sections` maps a feature id to `SaveSection(version, data)`, instead of the fixed fields `ledger, tasks, pin, fish` (spec sections 7.3 and 9). | With fixed fields every new feature must edit `SaveData` and the schema version, a guaranteed merge conflict for six people. With sections a feature owns and versions its own data; the frame never changes. Atomic write, `.bak`, `.corrupt-<millis>` and refusing newer versions are unchanged. |
| D-005 | `SaveMigrator` works on any JSON element and is used both for the file frame and for each feature's section. | One mechanism to learn instead of two. |
| D-006 | The `<millis>` in `save.json.corrupt-<millis>` is the last-modified time of the damaged file, not the current time. | The save store has no `Clock`, and rule 0.5 forbids reading the system time. A numeric suffix is added if the name is taken. |
| D-007 | New core packages `core.events` (`EventBus`) and `core.module` (`DomainFeature`, `FeatureContext`, `ServiceRegistry`), which the spec does not list (rule 0.1). | They are the extension mechanism that lets six people add features in parallel: a feature registers itself with one line in `DomainFeatures` instead of editing shared classes. |
| D-008 | `GameSession` has no public fields per service; services are looked up with `session.get(Type.class)`. `GameSessionFactory.create` takes a `CoreConfig` and the list of features (spec section 7.9). | Fixed fields would have to be edited for every new feature. |
| D-009 | No single `GameConfig` record (spec section 6). The core has `CoreConfig`; every feature has its own config record with a `defaults()` factory holding the spec values. | One shared config file would be edited by everyone. Values and the no-magic-numbers rule are unchanged. |
| D-010 | The UI does not call `saveNow()` after each action (spec section 8.6). Domain code calls `FeatureContext.requestSave()` and the session saves once at the end of the frame; `dispose()` still calls `saveNow()`. | Saving is a domain concern; a forgotten call in one screen would lose data. |
| D-011 | Domain packages are `domain.core.*` and `domain.feature.<name>.*` instead of the flat list in spec section 4. | Makes the boundary between the shared core and the independent features visible and checkable. |
| D-012 | The window title is "Mini-Aquarium", not "Mini-Akvaryum" (spec section 8.1). Package and project names keep `miniakvaryum`. | "Aquarium" is the spelling the player-facing language uses; see D-025. |
| D-013 | User-visible strings live in one `...Strings` class per feature plus `CoreStrings`, all in the `game` module, instead of a single `Strings` class (spec rule 0.6). | A single class would be edited by everyone. |
| D-014 | `Wallet` has a second constructor with a listener that is called after every recorded transaction. | Lets `EconomyFeature` publish `LedgerChanged` and request a save while `Wallet` itself stays free of core dependencies. The constructor from spec section 7.4 still exists. |
| D-015 | `Wallet` keeps running balances in memory (rebuilt from the entries on load) instead of summing the ledger on every `balance()` call. | The HUD reads balances every frame and the ledger grows with every pellet eaten. Balances are still derived and never saved. |
| D-016 | Service constructors from spec section 7 take a few extra parameters: the feature's own config record instead of `GameConfig`, and where needed an `EventBus` and an `onChange` callback. `PinService.state()` returns `Optional<PinState>`. | Consequence of D-009 (config per feature), D-007 (events) and D-010 (save requests). `Optional` avoids a null return while no PIN is set. |
| D-017 | `fish`, `food` and `world` are sub-packages of one feature `aquarium` (`feature.aquarium.api.fish` etc.), not three independent packages (spec section 4). | They depend on each other in both directions (`FishBrain` uses `FoodField`, `FoodService` uses `FishEntity`), so they cannot be separate features. |
| D-018 | `FishState` and `Pellet` have public getters and package-private setters; `FishEntity` changes its facts only through `recordFeeding()` and `addAquariumMillis()` (spec section 7.7 shows plain fields). | Enforces "the UI never edits fields of domain objects" (spec section 5) by the compiler instead of by convention. |
| D-019 | Skeleton methods throw `UnsupportedOperationException("TODO: ...")`. The one exception is `AquariumWorld.update`, which does nothing until implemented. | `update` runs every frame; throwing there would make the game unstartable for everyone until that one method is written. |
| D-020 | `PinService.setPin` refuses to replace an existing PIN (spec 7.5 mentions a verify-then-set call chain). | Changing the PIN is not in the scope of this milestone (spec section 15: no PIN recovery). |
| D-021 | Architecture rules are checked by `ArchitectureTest`, a plain JUnit test that scans the source files, instead of a library such as ArchUnit. | The spec allows no extra dependencies (section 3). |
| D-022 | The UI has the same plug-in structure as the domain: `GameFeature`, `UiContext`, `Navigator` and `MainLayout` in `game.core`; one package per feature under `game.feature`; the list `GameFeatures`. `MainScreen` contains no feature code (spec section 8.5 describes one fixed main screen). | Lets several people add buttons, status texts, layers and screens without editing a shared screen class. |
| D-023 | `PlaceholderTextures` (spec section 8.3) is split into `ShapeTextures` in the UI core (generic shapes, file-or-placeholder loading) and `AquariumTextures` in the aquarium UI feature (the fish and pellet images). | The core must not know fish; later features need placeholder shapes too. |
| D-024 | UI actions run through `BaseScreen.guarded`, which turns the `UnsupportedOperationException` of skeleton code into an on-screen message. | Keeps the game usable for everyone while features are still being written. |
| D-025 | All user-visible text is English, not German (spec rule 0.6 and section 15). The texts still live only in the `...Strings` classes of the `game` module. | Team decision. Because every text is in a `Strings` class, switching the language again means editing only those classes. |
| D-026 | `VerifyResult.attemptsLeft` is `pinMaxAttempts` for `OK` and `NOT_SET` and 0 for `LOCKED`; `lockedRemainingMillis` is 0 except for `LOCKED`. `verify` calls `onChange` only when the state really changed (a correct PIN with all counters already at 0 changes nothing). | The specification gives the numbers only for `WRONG` and `LOCKED`. While locked no attempt is possible, so 0 is the honest value; after `OK` or without a PIN the full number is available. |
| D-027 | In the parent area, "Edit" loads an ACTIVE task into the same form that creates tasks; the form then saves with "Save changes" or is reset with "Cancel". Reported (PENDING) tasks are listed first. Leaving the screen in any way (also closing the window) locks the parent session through `Screen.hide()`. | The specification names the buttons but not how editing looks. One form for both keeps the screen simple for parents; PENDING tasks first because they are what the parent has to act on. |
| D-028 | `PinServiceTest` runs with `pbkdf2Iterations = 1 000` instead of 120 000; the game itself uses the default config. A PIN is exactly `pinLength` ASCII digits `0`-`9` (other Unicode digits are refused). A PIN with the wrong format is refused with `IllegalArgumentException` and does not count as a wrong attempt. | Some tests check many PINs; the rules do not depend on the iteration count, so a cheap hash keeps the build fast. ASCII only, so that the PIN typed on the number pad and on the keyboard is always the same text. A typing mistake in the length is not a guess at the PIN. |
| D-029 | The UI screens read their limits from the default configs: `ParentGateScreen` uses `SecurityConfig.defaults().pinLength()`, `ParentScreen` uses `TasksConfig.defaults()` for the title length and the highest reward. The domain checks every value again. `ParentGateScreen` also shows a lockout that is still running when the screen is opened again (read from `PinService.state()`), and a PIN with too few digits only shows a message. | The game installs the features with the default configs (`DomainFeatures`), and the services do not expose their configs. Showing a running lockout right away avoids a child trying again and again without seeing why nothing happens. |
| D-030 | Deferred: `LevelRules.levelOf` (package 4) is not implemented yet and `LevelRulesTest` stays `@Disabled`. | Fish levels are not shown or used anywhere in the game yet (`levelOf` has no caller), so the game runs without it. To be done before the final demo (package 6 checks it). |
| D-031 | Deferred: the food display "stock (free)" (package 3, `EconomyGameFeature`) is not implemented yet; the status line shows the FOOD balance only. Food is debited when a fish finishes eating, not when a pellet is dropped (spec section 9.4), so the shown number changes only after eating. | The rules (`FoodService.available()`) are complete and tested; only the display is missing. To be done before the final demo. |
| D-032 | `FishBrainTest.failedClaimFallsBackToIdle` stays `@Disabled`. The fallback to IDLE in `FishBrain` is implemented, but the test is not written. | The brain asks `FoodField.nearestFree` for a FREE pellet and claims it in the next call; in single-threaded code nothing can happen in between, so the branch cannot be reached with the real (final) classes. Testing it needs a seam such as an interface for `FoodField`; the team decides later whether that is worth it. |
| D-033 | `FoodConfig.maxPelletsInWater = 5`: at most five pellets may be in the water at the same time. When a drop is refused, the UI shows "No food available" (spec text) if no pellet is in the water, and "Let the fish eat first!" if pellets are still in the water (limit reached, or all free food already lies in the water). | Not in the specification; added with package 3. Keeps the child from filling the water with pellets that only dissolve. Kept for now; the demo script (three pellets) is not affected. |
| D-034 | Deferred: the finished aquarium packages (`feature/aquarium/api/food`, `world`, `fish`) are not yet in `coverageGatedPackages` in `domain/build.gradle` (D-003). | Their coverage is already above 70 %; they are added together when package 4 is finished, so that the gate is changed only once. |
| D-035 | New feature `dirt` (scope extension; dirt was out of scope in the specification). A spot appears every 2 hours of game time, also offline through the credited gap, up to 12 spots (100 %). The child taps (5 taps per spot) or rubs (about 300 units per spot) the spots away; a spot's strength is its opacity. Wiping the last spot counts as a cleaning: its game time is saved (`lastCleanedGameMillis`, UC-4), the interval restarts from 0 so the next spot comes a full 2 hours after cleaning, and `AquariumCleaned` is published. In feed mode a tap drops a pellet instead of wiping. | Needed for UC-4 / TC-4. 12 spots in 24 h means an aquarium left alone for the longest credited offline time is completely dirty. Saving happens when a spot appears or disappears, not on every wiping frame. |
| D-036 | Core extension: `MainLayout.addWorldDragHandler(WorldDragHandler)`; `MainScreen` forwards finger movements over the aquarium to the registered handlers. | Wiping needs movements, and the main screen only forwarded taps. The change is additive: no existing behavior or signature changed. |
| D-037 | Core extension: `UiContext.restartFromSave()` rebuilds the session and the whole UI from the save file at the start of the next frame, without saving first. Used only by the developer tools for time travel: "+1 h / +6 h / +24 h" save the game, move the time anchor in the save into the past and restart, so the normal start-up credits the hours as offline time. Before the first jump the save is copied to `dev-checkpoint/` next to it; "Undo time" restores that copy. | Testing time-dependent behavior (dirt, fish age, later energy) by hand without editing `save.json`. Restarting from the file runs exactly the code path of a real break, so no feature needs special time-travel code. |
| D-038 | The reward fields of the parent area accept one digit more than the highest reward (4 digits for 999). | Fix of F-1 from the MS2 test run: with 3 digits, typing "1000" silently became "100". Now a too large value can be typed and is refused with the existing message; any 4-digit number is above 999, and no input can overflow an `int`. |
| D-039 | Accounts (V12, plan "Konten und Profil"). New core package `domain.core.account` (`AccountService`, `AccountStore`, `PasswordHasher`) and `game.core.account` (`AccountFlow` and its screens). `accounts.json` lies in the app folder; each account plays with its own save in `accounts/<id>/`, where `<id>` is a random 8-character id, not the username. `MiniAkvaryumGame` first shows Welcome / Sign up / Sign in (or starts the remembered account) and only then builds the session with that folder. The first account on a device takes over the save from before accounts existed (`save.json`, `.bak`, `dev-checkpoint`) by moving it. | Every account is its own world. A random folder name keeps usernames out of file paths. Moving (not copying) the old save keeps the coins, tasks and PIN of players who started before accounts. |
| D-040 | The parent PIN is not touched. Sign-up asks for no PIN and the security feature is unchanged; a new account simply has no PIN in its save, so the parent area asks for one the first time it is opened, exactly as before. Password reset uses a "safety color" (10 colors, picked at sign-up) instead of the PIN. | Team decision: the account work must not change anything that belongs to the parent area. |
| D-041 | Locks: 5 wrong passwords lock sign-in for 30 s, 60 s, 300 s, then 900 s (as the PIN); 3 wrong safety colors lock the reset for 1, 5, 15, then 60 min. Locks are measured with the wall clock because no game session exists before sign-in; setting the clock back to before the start of a lock does not shorten it. Passwords and the safety color are stored as PBKDF2 hashes (120 000 iterations, 1 000 in the tests). An unknown username gives the same message as a wrong password. | The safety color has only 10 values, so it can be guessed; the waiting times make guessing slow. This is accepted: the color helps a child get back into its own account and is no strong protection (known limit in the plan). |
| D-042 | "Remember me" exists on Sign in and on the last sign-up step. Only one account is remembered; signing in without ticking it forgets any remembered account, and "Sign out" forgets it too. | Otherwise a device would keep opening the account of a sibling who once ticked the box. |
| D-043 | Core extensions: `UiContext.account()` and `UiContext.saveFolder()`; the developer time travel uses the save folder of the signed-in account. Until the profile screen exists (V12 step 4), `MiniAkvaryumGame` adds a temporary "Sign out" button to the top bar; it first asks "Do you really want to sign out?" (`SignOutConfirmScreen`, Yes / No). | Time travel must edit the save of the account that is playing. The button makes switching accounts testable now and moves to the profile screen later. |
| D-044 | The picture step of sign-up offers the 18 avatars (`assets/avatars/<row>/<name>.png`, 512 x 512) and "Skip" (first letter in a colored circle). Camera and gallery come with the profile screen (V12 step 4). Usernames are ASCII letters, digits and underscore (3 to 15). | Avatars need no platform code; the camera needs the desktop spike first. ASCII usernames are easy to type on every keyboard and compare reliably without case problems. |
| D-045 | New feature `energy` (V12, plan "Energie und Schlafenszeit"): energy 0 to 100, kept with decimals, starts at 100 in a new game. Per hour it grows by 1 + (2 + level) for every fish in the aquarium, also while the app is closed (credited gap, at most 24 h, with the fish of the save). It is only spent through `EnergyService.spend(amount, refId)` (a game costs 20, `EnergyConfig.gameCost`); the same refId is never paid twice, and the last 50 refIds are kept in the save. Installed right after the aquarium. | Energy limits the minigames without punishing: 3 fish of level 1 give one game every 2 hours. Numbers from the plan; D-039 to D-044 are taken by the accounts branch. |
| D-046 | `FishLevels` decides the level of a fish for the energy rate; the game uses `FishLevels.ALL_LEVEL_ONE` until `LevelRules.levelOf` exists (D-030). "Active fish" are all fish in the aquarium until the inventory (V11) can take fish out. | `LevelRules.levelOf` still throws; the energy feature must not depend on unfinished code. When levels exist, one line in `DomainFeatures` changes. |
| D-047 | Core extension: `MainLayout.addStatusWidget(Actor)` puts a widget into the top bar after the status texts; the energy bar (bolt, bar, "Energy 45", soft glow at 100) uses it. The bolt is `assets/icons/energy.png`. The developer bar gets "E: 0" and "E: 100". | The top bar only took texts. Additive change like D-036. The developer buttons make the hand test of the plan possible: "E: 0", then "+1 h", "+6 h", "+24 h" give 10, 60 and 100. |
| D-048 | New feature `bedtime` (V12, plan "Energie und Schlafenszeit"): 21:00 to 07:00 is bedtime. `BedtimeService` answers `isBedtime()` and `bedtimeEndsAt()`, publishes `BedtimeStarted` / `BedtimeEnded` when the hour passes while the game runs, and hands out the greetings once: "Goodnight, little fish!" once per night (01:00 belongs to the night before), "Good morning, little fish!" once per day when the game is open between 07:00 and 12:00. The greeting dates are saved. The game shows a night-blue layer over water and sand (fading over 2 s) and a card that slides up for 3 s; a tap closes it. The card backgrounds are `assets/bedtime/goodnight.png` and `goodmorning.png` (1520 x 320); without them a simple card is drawn in code. Installed before the aquarium. | Bedtime only gives information and events; letting the fish sleep and closing feeding stays in the aquarium code of V10, which asks `ctx.require(BedtimeService.class)`, so the two work packages do not edit the same files. |
| D-049 | Core extension: `LocalClock` (local date and time of the device) and `AdjustableLocalClock`; `DomainFeatures.all(LocalClock)` takes it. The game creates one `AdjustableLocalClock` from the platform clock and the device time zone; the developer bar can shift it ("Clock: real" -> 21:00 -> 07:00 -> real; the matching banner appears at once, also when it was already shown that day) without touching the device clock. The shift is not saved. The developer bar's time text now stands right after the last button and reads "+52 h 00 min" (shorter, so all buttons fit), and `DevBar.addButton` returns the button. | The domain may not read the system time (`ArchitectureTest`), and `GameTime` cannot say what time of day it is. Known limit: a child who changes the device clock can play at night; recorded in the plan. |
| D-050 | New features `profile` (the favorite fish; without a choice the fish that lived longest in the aquarium) and `stats` ("My stats"). Most stats are read from the existing save: approved tasks, food eaten (sum of `feedCount`), coins received (positive coin ledger entries; spending does not lower it), fish count. Only cleanings (`AquariumCleaned`) and days played (local date at game start) are counted, from now on. Fish level shows 1 until V10. The profile screen opens from the child's picture at the left of the top bar; it is a child area without PIN. | A child who played before sees filled numbers at once. Levels and fish names are V10; the profile uses "Fish 1", "Fish 2" until then. |
| D-051 | Core changes for the profile: `UiContext` gives `accounts()`, `account()` (read fresh, so edits show at once), `pictures()` and `signOut()`; `Navigator.back()` returns to the previous screen; `AccountScreens` registers Edit profile, Your picture, Adjust your photo, Change safety color and the sign-out question for each session; `AccountPictures` draws avatars, photos and first letters for both the account screens and the game. The temporary "Sign out" button of the top bar is gone; "Sign out" is on the profile, after the question (D-043). `MainLayout.addStatusWidget` is the same change as on the energy branch (D-047). | Editing the account belongs to the core accounts code; the profile feature only opens these screens by id, as the architecture rules require. |
| D-052 | Profile photos: platforms give a `PhotoSource` to the game. The desktop uses the system file window (png, jpg); the camera is not offered until the webcam test on a real laptop (plan V12, step 0). "Adjust your photo" lets the child drag and zoom (buttons, mouse wheel, two fingers) inside a round frame; `PhotoFrame` holds the math (tested). "Use photo" saves the circle as `photo.png` (512 x 512, transparent corners) in the account folder; the original file is only read. The sign-up picture step still offers avatars only. | No platform library in the game module. A photo chosen during sign-up would need storage before the account exists; it can be added on the profile right after. |
| D-053 | On the birthday the profile picture gets a frame (`assets/profile/birthday-frame.png`: balloons, present, fish) together with "Happy birthday"; the small picture in the top bar gets it too (`birthday-frame-small.png`, picture 44 px so it fits the bar). The dev bar has a "Date" button: a small panel sets a pretend date (day, month, year with + and -, "Birthday", "Real date"). Only `AccountService.today()` uses it (birthday, sign-up age, days played); locks keep the real clock, and nothing is saved, so the real date is back after a restart of the app. | The birthday can be checked any day without changing the computer's date. |
| D-054 | `feature/v12` brings accounts, energy, bedtime and profile together (merged in this order onto the profile branch). Two dates exist side by side on purpose: the bedtime `LocalClock` (dev button "Clock") and the account date `AccountService.today()` (dev button "Date", D-053). The dev bar got narrower buttons ("Undo time" is now "Undo") so all nine buttons and the time text fit. | Each part was built and tested on its own branch; merging them before the next step (trophies) keeps the conflicts small. The two dev dates test different things and stay separate until a feature needs both. |
